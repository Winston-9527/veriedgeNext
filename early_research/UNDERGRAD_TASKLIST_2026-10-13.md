## 0. 背景：先用十分钟读懂我们在做什么

**场景**：许多边缘设备组成一个去中心化算力网络，用流水线方式跑同一个开源大模型。每个 provider 负责连续几层（一个"分片"），把中间结果（activation）传给下一个节点。算力按精度分档收费，比如 fp16 / int8 / int4。

**要抓的作恶行为**：
1. **降档**：收 fp16 的钱，实际跑 int8 或 int4；
2. **直通**：不计算，把上游 activation 原样传下去；
3. **篡改**：改动 activation 后再交给下一个节点；
4. **重放**：用别的请求或旧的 activation 冒充。

**难点**：诚实节点在不同 GPU 上算出来的结果也不会逐比特一致。检测方法必须做到两件事：容忍诚实节点之间的差异，同时抓住作恶造成的差异。

**目前的主线方案**：Route B 的 **PACT** 协议。节点先对自己输出的 activation 做哈希承诺，之后验证方才抽取随机投影方向；用投影后残差的能量（服从 χ² 分布）判断这个分片是否算错，并定位到具体节点。

**为什么需要你**：最近的实验（E0）发现了几件事，需要更多实验来确认或推翻：
- **同档诚实节点之间的差异可能接近 0。** 4B 模型、fp16 计算下，NVIDIA 和 Apple 的 top-1 输出几乎完全一致。但这只在一种硬件组合、而且只在输出 logits 上测过，**还没有在分片边界的 activation 上测过**。
- **最难抓的作恶是"单个分片 + 强量化器（GPTQ）"。** 它的误差只有诚实噪声的 2–4 倍。
- **计算精度用 bf16 时，诚实噪声会大很多**，所以协议规格应该怎么写，需要数据来支撑。

**你的硬件组合的价值**：你的笔记本（RTX 5060，Blackwell 架构）和服务器 RTX3090（Ampere 架构）是**两代不同的 NVIDIA GPU**。这正好是 E0 没有覆盖的诚实组合（E0 只比较了 NVIDIA 和 Apple）。

### 1.3 笔记本上的注意事项（排雷要点）

- **操作系统**：脚本是 bash 写的，建议用 Ubuntu 或 Windows + WSL2。
- **PyTorch 版本**：RTX 5060 是 Blackwell 架构（sm_120），需要 **CUDA 12.8 及以上编译的 PyTorch**（`cu128` 或更新）。老版本会报 `no kernel image`，先用 `torch.cuda.get_device_capability()` 确认。
- **4B 放不进 8 GB 显存**：用 `device_map` 加 `max_memory`，比如 `{0: "6GiB", "cpu": "10GiB"}`，让部分层的权重放在内存，前向时再搬到 GPU 上算。
  - **必须验证计算确实发生在 GPU 上。** 在 0.6B 上把"offload 模式"和"整模型放进显存"的输出逐位比较，应当完全一致。不一致就说明有层落到了 CPU 上计算，这本身就是一个必须记录的发现。
  - offload 会慢一些，跑完一遍 520 条 prompt 大约要数十分钟到一两个小时，属正常。
- **记录数值开关**：fp32 矩阵乘法在 Ampere 及以后的 GPU 上可能走 TF32。每次采集都要在 meta 里记下 `torch.backends.cuda.matmul.allow_tf32`、`torch.backends.cudnn.allow_tf32`、驱动版本和 CUDA 版本。
- **笔记本跑实验时**：插电源，用性能模式，避免中途休眠。

### 1.4 数据与脚本

- **prompt 数据**：`qwen_prompt_splits_stratified_v2_200_500.jsonl`（200 条 calibration、520 条 evaluation，sha256 前缀 `5f1be1ee`），已在交接包里。
- **现成脚本**：`early_research/E0/scripts/`，看各文件开头的 docstring：
  - `e0_build_contexts.py`：生成测试上下文；
  - `e0_capture_torch.py`：采集 torch 执行栈的输出（支持 `--layers` 只量化部分层）；

  - `e0_same_tier.py`：按档重算。
  - mlx 相关脚本在你的机器上用不到。
- **PACT 统计代码**：`research_routes/route_b_veriedge_system/experiments/pact_offline/`，主要是 `conditional_power.py`（给定误差比，算需要多少投影行 K）。

  3. **冒烟测试**：两台机器都用 0.6B 跑 `e0_capture_torch.py`（只取 8 条 prompt），确认能正常出结果。
  4. **给 `e0_capture_torch.py` 加一个 `--offload` 选项**，用 `device_map` + `max_memory` 实现，并在 0.6B 上做逐位一致性检查（见 1.3）。这是你写的第一段新代码。

#### T1：笔记本对 3090 的同档诚实对（logits 层面） ★
- **问题**：同一个 4B 模型、同一种精度，在 RTX 5060（Blackwell）和 RTX 3090（Ampere）上算，诚实差异有多大？E0 里 NVIDIA 对 Apple 的 fp16 档几乎为 0，换成两代 NVIDIA GPU 还成立吗？
- **做法**：
  1. 在 3090 上用 `e0_build_contexts.py` 生成 4B 的 `contexts_eval.jsonl`，拷到笔记本，核对 sha256；
  2. 两台机器各采集三个诚实档：
     - fp16：`--dtype float16`
     - bf16：`--dtype bfloat16`
     - int8 权重 + fp16 计算：`--quant rtn --bits 8 --group-size 128 --dtype float16`

     笔记本上加 `--offload`。
  3. 3090 上另外采集参考栈（`--dtype float32`）和全部作弊栈（整模型的 RTN-4 和 GPTQ-4；单分片的 GPTQ-4 和 RTN-4，用 `--layers 0-11`、`12-23`、`24-35`）；
  4. 以 3090 的同档栈作参考，笔记本的同档栈作诚实栈，仿照 `e0_same_tier.py` 计算诚实失配率、各作弊栈所需的 canary 数 N。
- **交付**：RESULT_MEMO（模板见 Route B 手册第 17.2 节），里面要有各档的诚实失配率，以及和 E0（NVIDIA 对 Apple）的对比表。
- **排的雷**：
  - "fp16 档诚实差异接近 0"在另一种硬件组合下是否成立；
  - "协议规定 fp16 计算后，int8 档的诚实噪声也接近 0"是否成立（E0 只测过 bf16 计算下的 int8 档）。

### 阶段二：核心排雷（第 3–5 周）

#### T3：在分片边界的 activation 上测同档诚实漂移 ★★（最重要）
- **问题**：PACT 检查的是**分片边界上的 activation**，不是最终 logits。笔记本对 3090 的同档诚实残差能量 `F_2 = ‖h − h_ref‖² / N`，在边界上是否也接近 0？深层边界会不会更大？
- **做法**：
  1. **写一个边界采集脚本** `e0_capture_boundary.py`：用 `output_hidden_states=True` 取第 11、23、35 层的输出（4B 共 36 层，对应三个分片的边界）。
     - **按原始 dtype 保存**：fp16 的值存成 fp16，不会丢信息，体积减半。
     - 每个执行栈约 0.5–1 GB，硬盘够用；可以先抽 200 条 prompt 试跑。
  2. **两台机器各采集同档诚实栈**：fp16、bf16、int8 + fp16。3090 再采集 fp32 参考。
  3. **统计**：每个 prompt、每个边界的相对残差 `‖h − h_ref‖ / ‖h_ref‖`，给出分布（中位数、p90、p99、最大值），C1/C2/C3 分开报告。
  4. **对比**：拿 Route B 的 720 池（MPS bf16 对 CUDA fp32，**跨精度**）在同样边界上的数字放在一起，说明"跨精度当诚实"会把诚实噪声高估多少。720 池的位置问导师。
- **交付**：采集脚本、各档残差分布表和图（图要能由 CSV 一键重建），以及 RESULT_MEMO。
- **排的雷**：Route B 最大的瓶颈是 C3 校准不住（6 个 prompt 时诚实超阈率 33%）。如果同档诚实残差在 C3 也接近 0，这个瓶颈基本消失；如果不是，要找出是哪个档、哪一层放大了诚实差异。

#### T4：单分片降档在边界上的残差，以及 PACT 需要的 K ★★
- **前置**：T3 的采集脚本。全部在 3090 上做。
- **问题**：只有一个分片用 GPTQ-4 或 RTN-4 降档时，它输出边界上的残差能量是同档诚实残差（来自 T3）的多少倍？PACT 需要多少投影行 K、多少个 canary 才能在 α = β = 10⁻³ 下检出？
- **做法**：
  1. 用 `--layers` 只量化一个分片，采集各边界的 activation；
  2. 算出每个 prompt 的作弊残差与诚实残差的比值；
  3. 用 `pact_offline/conditional_power.py` 的 χ² 方法换算出所需 K，再结合诚实残差的分布上界得到所需 canary 数。
- **交付**：表格"作弊方式 × 作弊分片 × 边界 × 档 → 残差比、所需 K、所需 canary 数"，以及 RESULT_MEMO。
- **排的雷**："PACT 用很小的 K（≤ 64）就能抓住单分片降档"。如果需要几百行以上，协议成本会成问题。
- **额外检查**：**作弊分片下游的边界**，残差是继续传播、被放大，还是被稀释？这决定了"第一个越界的边界"能不能准确定位到作弊节点。

#### T5：其他作恶方式的攻击目录 ★★
- **问题**：直通、篡改、重放，以及更隐蔽的"只跳过自己分片里的 1–2 层"，在边界上各产生多大的残差？
- **做法**：在 T3 的采集脚本里加注入钩子，3090 上实现以下攻击：
  - 直通：整个分片跳过，输出等于输入；
  - 部分跳层：跳过分片里的 1 层或 2 层，测几个不同位置；
  - 缩放：`h × (1 + ε)`；
  - 重放：用另一个 prompt 的边界 activation 冒充；
  - 小幅高斯噪声。
- **交付**：表格"攻击 → 相对残差 → 和同档诚实残差（T3）的比 → 是否可检"，以及每种攻击对最终输出的影响（top-1 是否改变）。
- **排的雷**：部分跳层可能残差很小，但对语义影响很大。如果存在这种"残差小、危害大"的攻击，materiality floor 不能只用 L2 范数来定。

### 阶段三：扩展探索（第 5–8 周，按兴趣选 1–2 个）

#### T6：诚实后端登记表 ★★
- **问题**：同档、同硬件下，换一个推理后端，诚实漂移会不会明显变大？
- **候选**：
  - **llama.cpp**：两台机器都能跑，GGUF 的 q8_0 版本约 4.3 GB，笔记本放得下；f16 版本用 `-ngl` 只把部分层放 GPU；
  - **vLLM**：只在 3090 上跑；
  - 不同 batch size；
  - sdpa 和 eager 两种注意力实现；
  - TF32 开和关。
- **交付**：表格"后端 × 档 × 机器 → 诚实失配率 / 边界残差"。凡是会破坏"同档诚实约等于 0"的后端，都要标出来，作为协议里"允许的实现清单"的依据。
- **排的雷**：E0 已经发现 bitsandbytes 的 LLM.int8 噪声比其他 8-bit 实现大几十倍。还有没有类似的"离群后端"？

#### T7：给被动 canary 的强攻击者——翻转预测器 ★★★（只需 CPU，第一周就可以开始）
- **问题**：E0 里的攻击者只会在"自己 margin 小的位置"切回全精度重算。更聪明的攻击者可以离线训练一个廉价分类器，预测哪些位置会翻转。它能用多少重算成本打穿被动 canary？
- **做法**：
  - 只用交接包里的 4B captures，笔记本 CPU 就够；
  - 特征：作弊栈自身的 top-5 logits、熵、margin、位置等；
  - 标签：该位置是否和参考的 top-1 不同；
  - 训练集和测试集**按 prompt 切分**；
  - 画出"重算比例 → 被动 canary 所需数量"的曲线，和 E0 里的 margin 规则对比。
- **交付**：曲线、RESULT_MEMO。
- **排的雷**：这个结果决定"被动 canary"能不能作为第一道筛查，还是一碰到聪明攻击者就失效。

#### T8：canary 能不能和真实请求区分开 ★★（笔记本即可）
- **问题**：流水线头节点能看到 prompt 明文。我们的 canary 都来自模板化数据集（"Explain X with Y"），一个简单的分类器能不能把它们和真实用户请求区分开？
- **做法**：找一个许可证允许的公开真实对话数据集（先列候选，和导师确认许可后再下载），训练一个简单分类器（TF-IDF + 逻辑回归即可），报告 AUC。再试着改写 canary（例如从真实数据集里抽取 prompt 作为 canary），看 AUC 能否降到接近 0.5。
- **交付**：AUC 表格，以及一条"canary 应该怎样采样"的建议。
- **排的雷**：如果 canary 很容易被认出来，头节点就可以只对 canary 老老实实计算。

#### T9：MoE 模型的诚实漂移 ★★★（选做，只在 3090 上做）
- **问题**：目标场景的模型很可能是 MoE。路由器选专家是离散的决策，微小的数值差异就可能让 token 换一个专家，从而放大诚实漂移。
- **做法**：选一个能放进 24 GB 的小 MoE 模型（先列候选和显存估算，和导师确认后再下载），在 3090 上比较 fp16 和 bf16、不同注意力实现下：
  - 专家选择的不一致率；
  - 边界残差。

  笔记本 8 GB 显存大概率放不下 MoE，所以这个任务不做跨机器比较。
- **排的雷**：如果 MoE 的路由翻转让同档诚实残差显著变大，整个方案在 MoE 上需要额外设计，例如把路由决策也纳入承诺。

## 3. 推荐顺序与依赖


## 4. 纪律（违反任何一条都可能让整组结果作废）

完整版见 Route B 学生手册第 16 节，这里列出最常踩的几条：

1. **calibration 和测试的 prompt 必须分开**。重复的随机 seed 不等于新的独立 prompt。
2. **每个数字都要标来源**：`measured`（实测）/ `derived`（推导）/ `assumed`（假设）。缺失的值写 NaN，不能填 0。
3. **负结果和失败的配置都要保留**，不能只交最好看的那个 seed、prompt 或边界。
4. **图必须能从同目录的 CSV 一键重建**，不能手工抄数。
5. **跨机器比较之前，先核对 `contexts_eval.jsonl` 的 sha256 一致**。每次采集都要在 meta 里记录 GPU 型号、驱动、CUDA、torch 版本、TF32 开关，以及是否用了 offload。
6. **INCONCLUSIVE 不能被悄悄算作 PASS**，也不能从分母里去掉。
7. **服务器礼仪**：不 kill 别人的进程；长任务用 `nohup` 并留日志；用完就删掉大的中间文件。
