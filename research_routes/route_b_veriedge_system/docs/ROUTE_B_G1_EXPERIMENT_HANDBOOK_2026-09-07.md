# G1 科研实验手册：用千问 Qwen3-0.6B 检查“正常差异”和“有害修改”

版本：2026-09-07，新生执行版。  
读者：第一次参加科研的大一学生。  
状态：实验计划，不是结果报告。下面标为“需要编写”的程序目前不能直接运行。  
模型统一使用：**`Qwen/Qwen3-0.6B`**，固定同一个模型版本和 tokenizer。不要擅自换成 0.5B、其他 0.6B 模型或其他微调版本。

## 1. 你在研究什么？

千问生成答案时，内部会产生许多数值。我们在模型的三个位置取出这些数值，称为 C1、C2、C3 检查点。

同一个问题，用两种正常的计算设置运行，内部数值也可能略有不同。例如，计算精度不同会产生舍入差异。我们希望一个检查程序做到两件事：

- 正常计算有小差异时，不轻易报错。
- 有人修改内部数值并使答案变错时，尽量发现问题。

PACT 是我们要研究的检查方法。它先把本次内部数值保存并绑定，再生成随机检查规则。攻击程序必须先交答案，不能看过本次检查规则再改答案。

**本项目最重要的问题：有没有一种修改，能让答案变错，但数值差异小到与正常计算难以区分？** 找到这种情况也是有价值的科研结果，不是实验失败。

你最终交付的是可信的数据和结论，不需要保证 PACT 一定有效。

## 2. 先认识这些词

| 词 | 在本实验中的意思 |
|---|---|
| prompt | 输入给模型的问题或指令 |
| 激活、张量 | 模型运行到某个位置时的一组数；可以先把它看成大数组 |
| actual | 这次被检查的计算结果 |
| reference | 另一次独立运行得到的参考结果；不是人工编造的数据 |
| 残差 | actual 减去 reference，表示两次计算差了多少 |
| K | 随机检查的数量；通常越多越费时，也更容易准确估计差异 |
| seed | 随机种子，用来生成可复现的随机检查规则 |
| 承诺、root | 对保存的张量计算哈希，像文件指纹；改文件后指纹也会改变 |
| 校准集 | 用来确定“正常差异通常有多大”的问题集合 |
| 测试集 | 方法定好之后才用来考试的问题集合，不能拿来反复调参 |
| 误报 | 正常任务被错误地判为 FAIL |
| 升级 | 当前检查拿不准，请更强的检查方法处理；不代表已经发现攻击 |

PACT 的三个结果：**PASS = 当前证据允许通过；FAIL = 差异超过规则；INCONCLUSIVE = 还不能确定。** PASS 不等于答案在知识或语义上必然正确，FAIL 也不自动证明有人故意作弊。

## 3. 任务边界：先做小，再做严谨

### 3.1 统一的第一轮设置

- 模型：`Qwen/Qwen3-0.6B`。记录实际下载的 revision、权重和 tokenizer 标识。
- 先研究处理输入问题时的三个检查点，再让模型继续生成答案。暂不研究逐 token 的 KV cache 攻击。
- 默认使用确定性的生成方式：`do_sample=False`，固定最大新生成 token 数；建议开发阶段为 32，正式值在看测试结果前固定。
- 固定聊天模板及思考模式。若所用 tokenizer 支持 `enable_thinking=False`，第一轮统一关闭；否则记录实际模板，不能两组使用不同模式。
- C1/C2/C3 由指导者和学生在 E02 中选定，记录精确层号、模块名及取值位置。不要凭印象填写模型层数。
- 首轮只用一对真实运行配置。参考配置可先尝试 FP32，另一配置选本机实际支持且获准作为正常执行的 BF16/FP16。若设备不支持，不强行使用。
- 两次计算使用完全相同的模型权重、输入 token 和模板。不同设置要分别真正运行，不能对一份张量加噪声冒充另一份正常结果。
- PACT 检查声明保护的全部坐标。旧文档中的“选 16 个 token”不能直接作为本项目的全覆盖检查。

### 3.2 谁负责哪些工作？

你可以独立做：整理数据、运行已有脚本、画图、核对文件、记录问题、实现经过指导者确认的小模块。

指导者需要帮助确认：检查点位置、两种诚实配置、攻击目标、置信区间和停止规则。E09 的梯度攻击较难，可以结对完成。暂时不理解推导时，先理解输入和输出，不能自行删除统计步骤。

### 3.3 单机是否够用？

| 工作 | 单机结论 |
|---|---|
| 已有张量分析、绘图、协议逻辑 | 普通 CPU 可以完成 |
| Qwen3-0.6B 双执行 | 可以在一台机器顺序运行；先确认内存和后端 |
| 修改激活后继续生成 | 单机可以，需完成注入程序 |
| 梯度/EOT 攻击 | 单机可以，推荐可用加速器；先测时间和内存，CPU 可能太慢 |
| 证明多个不同硬件都有效 | 本机没有对应硬件就不能完成；需要其他机器真实采集后再集中分析 |

“0.6B 模型能加载”不意味着反向传播也一定装得下。不要承诺固定显存要求，用 E00 的小试验确认。单机模拟发送方、接收方和参考方，只能检查代码逻辑，不能证明真实多方不串谋。

## 4. 做实验前必须遵守的六条规则

1. **问题分三份。** 开发集用于调代码，校准集用于定正常范围，测试集用于最终考试。相同问题和近似改写不能跨集合。
2. **正常数据必须真实运行。** 加噪声只属于人工篡改实验。
3. **先保存攻击，再产生最终 seed。** 不能看过最终检查结果后重新修改同一个攻击。
4. **问题数和重复次数分开。** 一个问题跑 1000 个 seed，仍然只有一个独立问题。
5. **保留所有结果。** 报错、内存不足、未产生危害、未检测到攻击，都要记录。
6. **先定标准，再考试。** 不得看完测试结果才换阈值、删困难问题或改变“有害”的定义。

## 7. E00：我的实验条件够不够？

**目的：** 避免做到一半才发现没有问题文本、模型版本不一致或电脑跑不动。

**要验证：** 能否用 Qwen3-0.6B 运行同一问题两次？能否保存张量？后续攻击是否能反向传播？

**怎么做：**

1. 记录操作系统、CPU/GPU、可用内存、Python、torch 和 transformers 版本。
2. 确认模型 ID 是 `Qwen/Qwen3-0.6B`，记录实际 revision；检查 tokenizer 和聊天模板。
3. 用两个短问题做前向运行，保存答案、耗时和峰值内存。
4. 尝试第二个真实正常配置，记录支持或报错。两个模型可以轮流加载。
5. 在支持梯度的模型配置上做一次小的激活梯度计算；这里只检查能否运行，不做正式攻击。
6. 清点已有张量有没有对应原问题。没有原问题的历史张量只能用于部分离线分析。

**交付：** 通用五件套，外加 `environment.json`、`asset_list.csv`。资产表每行写“已有/缺失、在哪里、用于哪个实验”。

**怎样判断：** 两配置和梯度都可运行，继续；只有一个配置可运行，可以先做 E01 和同配置重复，但不能宣布异构实验就绪；缺模型/问题/梯度则明确列出阻塞项。

**单机：** 可以。不同厂商硬件如果本机没有，要写“需要外部设备”，不能写“模拟完成”。

**单机：** CPU 可以，不需要下载模型。

## 9. E02：我取到的数值和修改方式正确吗？

**目的：** 排除“实验工具自己把答案弄错”的情况。

**要验证：** 不修改数值时，加上实验程序是否仍得到相同结果？修改指定检查点时，后续计算是否真的用了它？

**怎么做：** 用 8–16 个开发问题，分别检查 C1/C2/C3。

1. 写出模型模块清单，与指导者确定三个检查点。保存完整模块名、层号和张量形状。
2. 同一问题分别运行 actual/reference，保存各自的原始张量。
3. 对比三种程序：原模型；安装 hook 但不修改；保存张量再原样放回。
4. 比较模型输出分数和生成文本。先用同配置真实重跑确定合理数值容差，再固定容差，不得依据攻击效果放宽。
5. 加一个小的已知修改，确认目标位置改变、下游使用了新数值，其他位置没有被代码意外替换。
6. 变长问题逐个保存，不能强行把不同长度张量堆成同一形状。

**交付：** 通用五件套；`checkpoints.json`；三种零修改路径的逐问题对比表；每个检查点一份小张量样例。

**怎样判断：** 零修改等价才进入攻击实验。若零修改就改变答案，先修程序，不算攻击成功。

**单机：** 可以，需运行模型。不要同时加载不必要的模型副本。

## 10. E03：正常差异大概长什么样？

**目的：** 先用小数据发现明显问题，避免盲目采集几百个问题。

**要验证：** 正常差异是否随检查点或输入长度改变？完整差异能否与明显篡改分开？

**怎么做：**

1. 取 30–50 个开发问题，两种正常配置各真实运行。
2. 其中 10–15 个问题再真实重跑 3–5 次，观察“同一配置自己重复”的差异。
3. 计算每个张量的平均平方差：`F2 = mean((actual-reference)^2)`。
4. C1/C2/C3 分别画分布图，标出长度、异常值；不得只画平均值。
5. 加入少量 E07 的修改，比较正常与修改的 F2。
6. 做一个不用随机投影、直接读取完整 F2 的对照。如果完整 F2 都重叠，就不能指望单纯增大 K 自动解决。

**交付：** 通用五件套；`energy_by_prompt.csv`；三个检查点的分布图；异常问题列表。

**怎样判断：** 正常与修改明显分开，继续；正常差异有极端值，先查代码和配置；有害修改与正常重叠，优先做 E09。这里样本少，不能做正式 1% 误报结论。

**单机：** 可以。采集需模型，画图只需 CPU。

## 11. E04：正常任务会不会被误判？

**目的：** 给检查程序一次真正的独立考试。

**要验证：** 用一批问题定规则后，在没见过的问题上，误报是否受控？是否多数问题能直接 PASS？

**怎么做：**

1. 开发集之外，准备校准集和测试集。建议首个配置对用 300–500 个校准问题、至少 300 个独立测试问题。
2. 记录来源、去重方法、长度范围和任务类型。同一问题及近似改写放在同一集合。
3. 每个问题真实运行两种配置；记录截断、失败和缺失，不因结果不好而删除。
4. 只用校准集确定正常范围。指导者帮助实现任务级误报控制：三个检查点中任意一个错误 FAIL，都算该任务误报。
5. 固定阈值和规则后再运行测试集。记录 PASS、FAIL、INCONCLUSIVE，不只报误报率。
6. 同时提供误报率的置信上界，由统计脚本计算并经指导者核对。300 个问题零误报能支持约 1% 的单侧 95% 上界；300 个有误报时不能照抄这个结论。

**交付：** 通用五件套；三个集合的清单及哈希；校准阈值表；逐任务三态表；误报数/总数/上界；PASS 和不确定比例。

**怎样判断：** 正式目标是任务级误报上界不超过预定目标（默认方向为 1%），且 PASS 比例达到事先约定值。不能把所有问题都判成“不确定”来获得零误报。PASS 比例门槛由指导者在考试前填写。

**单机：** 可以，限实际运行的配置对；可以分批采集，但不能修改已冻结划分。

## 12. E05：多查几次真的更好吗？

**目的：** 检查随机检查数量 K 的作用，以及逐步加查会不会引入误报。

**要验证：** K 增加后估计是否更准？容易任务能否少查？不同检查点需要的数量是否不同？

**怎么做：**

1. 用冻结数据比较 `K=8,16,32,64,128,256,512,1024`。
2. 比较直接看完整 F2、理想 Gaussian 投影和实际 G16 实现。
3. 同一张量重复生成检查，仅用于观察随机性；不能把重复次数算成新的问题数。
4. 加入“从小 K 开始，拿不准就继续”的策略。规则和每轮允许错误的预算须在正式测试前固定。
5. 记录每个问题停止在哪个 K，以及最终三态、耗时和证据字节数。
6. 核对加查用同一张量承诺和预定投影前缀，没有途中换数据或换规则。

**交付：** 通用五件套；各 K 的结果表；停止 K 分布图；Gaussian/G16 对照表；实际使用的区间计算方法。

**怎样判断：** 少量检查就能稳定判断是好结果；只有大 K 有效则把成本交给 G0；完整 F2 也无法分开则不是 K 不够。多轮检查和 G16 的统计保证需要指导者核对，不能直接套固定一次检查的公式。

**单机：** CPU 可以。矩阵分块生成，不一次性保存全部大矩阵。

## 13. E06：换设置后旧规则还可靠吗？

**目的：** 检查方法的适用范围，防止把一个配置的成功推广到所有情况。

**要验证：** 精度、软件或问题类型变化后，旧阈值是否还适用？程序能否识别配置不匹配？

**怎么做：**

1. 一次只改变一个因素，先用 30–50 个新开发问题小试。
2. 对比原配置+原规则、新配置+旧规则、新配置被识别为不匹配三组。
3. 对新配置重新采集校准集，使用另一份独立测试集检查能否恢复。
4. 另做长度或任务类别变化。注意：模型版本不变不代表问题分布没变；没有漂移监控程序，就不能声称自动发现这种变化。

**交付：** 通用五件套；`changed_factor.json`；三组对比图；哪些配置需要重新校准的列表。

**怎样判断：** 小试只能发现风险；若要对新配置声称 1% 误报，仍按 E04 计算正式样本量。配置变化后规则失效，应限制范围或重新校准。

**单机：** 本机支持的精度/软件/问题变化可以；本机不存在的硬件需要外部采集。

## 14. E07：普通修改能否造成实际错误？

**目的：** 把“数字变了”和“任务真的做错了”联系起来。

**要验证：** 哪些简单修改会产生实际危害？PACT 能否发现？

**怎么做：**

1. 先选 20 个开发问题，三个检查点分别测试。
2. 做加噪声、数值缩放、相同形状的旧任务张量替换。跳层等操作只有真正实现后才标记，不用噪声冒充。
3. 每类选择三个预定强度，保留所有结果。
4. 让模型真实继续生成，保存原答案和修改后答案。
5. 第一轮主任务建议选择有明确正确答案的短任务，例如受控算术、分类或信息提取。固定答案解析和评分规则；题目模板产生的近重复不能跨数据集合。
6. 同时报告原任务正确率，以及原来正确的任务被改错的比例。原来已经错误的任务不能算成“被攻击弄错”。
7. 在最终随机检查前先保存修改后的张量并记录哈希。

**交付：** 通用五件套；原问题/正确答案/原输出/修改输出/是否真正变错的表；危害与 F2 散点图；至少三个可追溯案例。

**怎样判断：** 文本换了表达但答案仍正确，不算主要危害。能发现大噪声只是入门结果，下一步必须做专门针对检查器的攻击。

**单机：** 可以，需模型；张量注入程序在 E02 验证后复用。

## 15. E08：提前知道检查规则会怎样？

**目的：** 验证 PACT 为什么要求“先保存结果，后公布随机检查”。

**要验证：** 攻击者提前看到检查矩阵，是否能找到检查不到的修改？后公布矩阵时是否不同？

**怎么做：**

1. 先运行已有零空间小实验，理解“修改存在但投影几乎为零”。由指导者解释线性代数，不必第一天独立推导。
2. 建立两组：先看到本次矩阵再选修改；先固定修改再生成本次矩阵。
3. 对比投影差异、F2 和通过率；两组攻击预算一致，记录时间顺序。
4. 能恢复路线 A 的旧攻击时，额外做旧检查和新 PACT 的对照；缺代码则明确标缺失。
5. 若声称产生实际危害，必须像 E07 一样继续运行模型并评分。现有几何脚本没有完成这一步。

**交付：** 通用五件套；两组时序日志；矩阵乘修改的误差；通过率表；如有语义结果，另附任务评分。

**怎样判断：** 已知矩阵时保持投影不变是预期负对照，不表示 PACT 已被合法时序攻击击败。若该对照反而总被发现，先查构造和数值误差。几何隐形也不保证一定产生语义危害。

**单机：** 几何部分 CPU 可以；输出危害部分需要模型。

## 16. E09：能否找到“小改动，大错误”？

**目的：** 这是 G1 最重要的探索：主动寻找方法的弱点。

**要验证：** 攻击者不知道最终检查规则，能否让任务出错，同时把 F2 保持得很小？

**怎么做：** 建议与指导者一起完成优化器。

1. 先用 8 个开发问题和一个检查点验证梯度方向、注入位置和输出评分。
2. 做三种攻击：只追求弄错答案；在弄错答案的同时减小数值变化；同时尝试躲过许多随机检查。这第三种叫 EOT。
3. 开发阶段可先试 50/200 步、2 次重新初始化、每步 8/32 个检查 seed。记录耗时，正式预算随后冻结。这些是起步参数，不保证足够强。
4. 攻击优化用一批 seed，选候选用另一批；最终测试 seed 在张量保存并哈希后才产生。三个集合不能重合。
5. 先在 20–30 个开发问题扩展到三个检查点，确认优化有效，再冻结正式攻击问题集与预算。
6. 对冻结的攻击可用 256 个最终 seed 估计随机通过率；统计结论仍按问题聚类，不能说样本数增加了 256 倍。
7. 比较完整 F2、Gaussian、G16、固定 K 和逐步 K。优化时借用了参考张量或可微替代模型，必须写清攻击者额外知道什么，并在目标配置真正测试。

**交付：** 通用五件套；优化过程曲线；seed 分组清单；攻击张量哈希；全部攻击尝试及成功造成危害的子集结果；危害—F2 图；每种逃逸的可重现案例。

**怎样判断：**

| 结果 | 你应该怎样解释 |
|---|---|
| 答案明显变错且稳定 FAIL | 支持对这些攻击有效，继续独立复核 |
| 答案变错且多数 INCONCLUSIVE | 只能说明需要升级；升级没做就不能算检测成功 |
| 答案变错、F2 正常、稳定 PASS | 重要弱点；重复核对并保存反例 |
| 完整 F2 能发现但小 K 不能 | 检查预算问题，核算增加 K 的代价 |
| 攻击没能把答案弄错 | 可能攻击还不够强，不能据此宣布检查器安全 |

**单机：** 可以，需可微模型和足够内存。量化后端不能反向传播时，先用可微配置开发，迁移到目标配置后重新实测；不得把替代模型结果当目标模型结果。CPU 耗时由小试决定。

## 17. E10：能否通过换文件或拖延作弊？

**目的：** 检查统计方法之外的程序漏洞。

**要验证：** 保存结果后换张量、复用旧回执或超时不交，会不会被当成 PASS？

**怎么做：** 在已有协议测试中增加或核对以下场景：改 actual root、改接收字节、改 reference、复用旧 task/boundary、复用 seed、改变 K 前缀、换校准版本、缺回执、延迟、重启后再次裁决。

如果审计调度器还没实现，“预测会不会被审计”和“反复换 root 选择有利审计”就标为未实现，不能拿其他测试替代。单机 seed 统计看起来随机，不等于已经证明现实随机源不可预测。

**交付：** 通用五件套；一张“操作—预期结果—实际结果—是否通过”的表；至少一条正常路径和每类异常日志。

**怎样判断：** 冲突拒绝，超时 ABORTED，不能自动 PASS。ABORTED 是协议中止，不算语义检测成功。

**单机：** CPU 可以，用多个对象或进程模拟角色。真实网络和多方信任留给后续阶段。

## 18. E11：整理结论，而不是挑最漂亮的图

**目的：** 给指导者一个可以决定继续、补实验或换方向的结果包。

**要验证：** 正常任务能否通过？有害修改能否发现？代价是否值得？哪些情况还不知道？

**怎么做：**

1. 正常任务报告：误报数/总数、置信上界、PASS 和 INCONCLUSIVE 比例。
2. 攻击报告：全部尝试数、真正造成危害数，以及有害任务的 PASS/FAIL/INCONCLUSIVE；两个分母都要有。
3. 每个检查点、配置和攻击类别分开列，再给预先规定的任务级汇总。
4. 对同一问题的重复 seed 先做问题内汇总，再计算跨问题不确定性。统计程序交指导者复核。
5. 把 K、投影时间、证据字节、正常/攻击升级率交给 G0 成本实验。升级没实现时，其效果和成本写 UNKNOWN。
6. 每个实验标已完成、失败、缺条件或未实现；列出本机实际支持的结论范围。

**交付：** 通用五件套；`G1_DECISION_REPORT.md`；`g0_inputs.csv`；全部实验索引和复现说明。

**怎样判断：**

- **继续：** 正常任务大多正常通过，有害攻击按事先标准被检测或有效升级，成本回填后仍值得研究。
- **补实验：** 只在部分配置有效，或升级效果、攻击强度还不确定。
- **改设计：** 多数正常任务拿不准，或有害修改稳定伪装成正常数值差异。
- **缺条件：** 不能跑真实双执行、没有有效攻击路径等。缺条件不等于方法无效。

**单机：** 汇总用 CPU。不能把单机耗时写成真实三节点性能。

## 20. 已有代码的两个重要提醒
